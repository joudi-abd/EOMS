# نظام الحضور - تحديث السماح وشرائح التأخير (V2)

هذا تنفيذ Backend داخل وحدة HR، يستند إلى commit `db3c81c`. تُستخدم واجهات المشروع الحالية وSanctum لحسابات المستخدمين. لا توجد تغييرات على مشروع الفرونت.

## القواعد المطبقة

- السبت إلى الخميس، 09:00 إلى 16:00 بتوقيت `Asia/Damascus`. الجمعة عطلة أسبوعية.
- لا توجد استراحة مخصومة، ولا حاجة لتسجيل الخروج والعودة أثناء الاستراحة.
- السماح الافتراضي 45 دقيقة من بداية الدوام: حتى 09:45:00 لا تأخير محتسب. ما بعد هذا الحد وحتى 10:59:59 يحتسب ساعة، 11:00:00 إلى 11:59:59 ساعتين، 12:00 ثلاث ساعات، وهكذا.
- الوضع الجديد `completed_blocks`: بعد تجاوز السماح، تُحتسب الشرائح المكتملة من بداية الدوام وبحد أدنى شريحة واحدة. الشريحة الافتراضية 60 دقيقة، ويمكن لـ HR تعديل `late_block_minutes` مع الدوام والسماح.
- المقارنة بالثواني الفعلية: لا نقرب 10:59:59 إلى 11:00. `late_actual_minutes` يقرب الدقائق الفعلية للأعلى للعرض، بينما `late_minutes` ناتج قاعدة الشرائح وقد يكون أقل أو أعلى من التأخير الفعلي.
- أوضاع V1: `threshold_full` و`excess_only` تبقى مدعومة للسياسات القديمة، ولا تتغير السجلات السابقة إلى الشرائح الجديدة تلقائياً.
- العمل الفعلي بالدقائق الكاملة من أول حركة إلى آخر حركة معتبرتين. لا يُعوّض التأخير بتمديد نهاية الدوام تلقائياً.
- الوضع الافتراضي `first_last` هو افتراض تشغيل معلن: يفسّر أول وآخر حركة، ولا يثبت اتجاههما فعلياً. مع أكثر من حركتين تظهر ملاحظة. يمكن اختيار `directional` عند التحقق من حالات الجهاز. لا يدعم هذا الإصدار حساب مغادرات واستراحات منفصلة.
- الحركات من النوع نفسه خلال 60 ثانية من آخر حركة معتبرة لا تكوّن فترة عمل مستقلة؛ تبقى جميع الحركات الأصلية محفوظة.
- بصمة واحدة لا تنتج خروجاً افتراضياً أو ساعات مكتملة. الساعات المجهولة `null` وليست صفراً.
- الوقت الإضافي المعروض بعد 16:00 معلومات غير معتمدة، ولا توجد خصومات أو استحقاقات مالية تلقائية.
- تاريخ إنهاء الخدمة آخر يوم ضمن الخدمة. حالة `on_leave` الحالية ليست تقويماً تاريخياً للإجازات؛ تتطلب مراجعة اليوم الحالي وتمنع اعتماده حتى التسوية. لا توجد وحدة إجازات أو عطل رسمية مؤرخة في هذا الإصدار.
- لا يوجد دعم وردية ليلية أو جداول فردية مختلفة بعد؛ الجدول موحد لكل الموظفين وله نسخ مؤرخة لا تتغير بأثر رجعي.

## التثبيت

انسخ ملفات الحزمة إلى `eos-backend` مع دمج الملفات الموجودة إذا تغيرت بعد commit الأساس. شغل من داخله:

```bash
php artisan optimize:clear
php artisan migrate
php artisan attendance:configure-defaults
php artisan db:seed --class="App\Modules\HR\Database\Seeders\AttendancePermissionSeeder"
php artisan test --filter=AttendanceTest
php artisan test
php artisan route:list --path=attendance
```

Seeder الحضور يضيف الصلاحيات ولا يحذف تخصيصات الأدوار. تعديل RolePermissionSeeder ضمن الحزمة مخصص أيضاً لتثبيت جديد؛ لا حاجة لإعادة تشغيل Seeder الأدوار العام على نظام مخصص قائم.

لا تنفذ `migrate:fresh` على بيانات المكتب. اختبارات `RefreshDatabase` تستخدم قاعدة `eoms_test` المنفصلة حسب إعداد المشروع.

جدولة السيرفر: `schedule:run` كل دقيقة. أضيف `attendance:recalculate` كل 15 دقيقة لمعالجة اليوم واليومين السابقين. لمعالجة يوم أقدم:

```bash
php artisan attendance:recalculate --date=2026-10-29
```

لا تحذف أوامر جدولة العقود وتنظيف المستندات الموجودة. طلب التقرير أو تفاصيل اليوم يعيد تحديث الإسقاط أيضاً. الأيام المعتمدة لا تُستبدل؛ يظهر `pending_changes` عند اختلاف البيانات.

## ترقية سياسة مستخدمة دون تغيير التاريخ

المهاجرة الجديدة تضيف `late_block_minutes` و`overtime_multiplier` إلى السياسات و`model` إلى الأجهزة. لا تعدل ملفات migrations القديمة ولا تحتاج migrate:fresh.

على تثبيت جديد غير مستخدم وبسياسة bootstrap الأصلية فقط، تتبدل قيمها الافتراضية إلى السماح 45 دقيقة و`completed_blocks`. أما إذا وجدت حركات أو أيام حضور أو تخصيصات، تُترك السياسة كما هي لحماية التاريخ.

للمشروع القائم، الأمر `attendance:configure-defaults` ينشئ نسخة القواعد الجديدة من الغد بتوقيت المكتب ويطبع تاريخها. يمكن تمرير `--from=YYYY-MM-DD` لتاريخ لاحق. يرفض التاريخ الماضي واليوم نفسه، ويرفض تاريخاً توجد فيه سياسة بدلاً من استبدالها. إذا جرى تشغيله مرتين لن يكرر السياسة ولن يغيرها. يُبقي النسخ المجدولة بعد ذلك التاريخ؛ راجع قائمة السياسات حتى لا تفاجأ بسريان نسخة مجدولة أخرى.

الطريقة المعتادة بعد ذلك هي إنشاء سياسات مستقبلية من شاشة HR عبر POST `/attendance/policies`، وليس إعادة تشغيل أمر التثبيت. عند الإنشاء اختَر `completed_blocks` لتطبيق الشرائح المتفق عليها.

## فصل اتصال الجهاز عن API المستخدم

هذه الحزمة توفر مستقبل JSON لبرنامج وسيط موثوق، وليست محوّلاً أصلياً لبروتوكول ADMS أو SDK لجهاز iFace 880 Plus. الربط المباشر بالجهاز يحتاج فحص firmware وعينة سجلات وتجربة فعلية. لا تضبط عنوان ADMS في الجهاز على هذا المسار وتتوقع أنه سيفهم JSON.

على السيرفر العام يلزم HTTPS. مسار الاستقبال يرفض HTTP خارج `local/testing`. إذا كان TLS ينتهي عند reverse proxy، يجب ضبط Laravel Trusted Proxies إلى البروكسي الحقيقي بطريقة صحيحة؛ لا تثق بعناوين غير محدودة لمجرد تجاوز الفحص. في الإنتاج تجنب تسجيل Authorization أو توكن الجهاز في access logs.

توكن الجهاز مختلف عن توكن Sanctum. يُعرض مرة واحدة عند إنشاء الجهاز أو تدويره، ويحفظ الخادم SHA-256 فقط. تعطيل الجهاز يوقف استقبال توكنه. التوكن يتيح إرسال سجلات لذلك الجهاز فقط، ولا يتيح عرض الموظفين.

## إدارة الجهاز والربط

كل المسارات أدناه تبدأ بـ `/api/v1`. إدارة الأجهزة تتطلب `attendance.manage`، والسياسات المقروءة `attendance.view`.

| الطريقة والمسار | المدخلات أو النتيجة |
| --- | --- |
| GET `/attendance/devices` | قائمة دون token أو token_hash |
| POST `/attendance/devices` | `name`, `serial_number`, و`model` اختياري وافتراضه `iFace 880 Plus`؛ يرجع `data.device` و`data.token` مرة واحدة |
| PATCH `/attendance/devices/{id}` | `is_active` فقط؛ لا تغيير لمعرّف الجهاز أو توقيته التاريخي |
| POST `/attendance/devices/{id}/rotate-token` | إبطال القديم وإرجاع توكن جديد مرة واحدة |
| GET `/attendance/devices/{id}/bindings` | روابط مرقمة؛ الموظف ورقم الجهاز وفترة الربط |
| POST `/attendance/devices/{id}/bindings` | `employee_id`, `device_user_id` نص, `valid_from`, `valid_to` اختياري |
| POST `/attendance/bindings/{id}/close` | `valid_to` اليوم أو تاريخ لاحق؛ الربط المغلق لا يعدّل مجدداً |
| GET `/attendance/unmatched-punches` | أحداث مجهولة؛ فلتر `device_id`, و`per_page` من 1 إلى 100 |
| GET `/attendance/policies` | نسخ السياسات المؤرخة |
| POST `/attendance/policies` | نسخة جديدة من الغد أو بعده؛ لا تحديث أو حذف النسخ القديمة |

لا يستخدم الربط حقل الموظف القديم `biometric_code` تلقائياً؛ الحقل القديم رقمي، بينما الربط الجديد نصي ومؤرخ ولكل جهاز. أنشئ الربط صراحة لتجنب نسب سجلات إلى موظف غير صحيح. الرمز `00105` يختلف عن `105` ما لم تؤكد عينة الجهاز خلاف ذلك. يسمح بنفس الرمز لموظف آخر في فترة لاحقة غير متداخلة، ويحفظ صاحب الحركات المرتبطة سابقاً. عند إنشاء ربط جديد تعاد مطابقة الحركات المجهولة داخل فترته فقط.

مثال ربط:

```json
{"employee_id":12,"device_user_id":"105","valid_from":"2026-10-29"}
```

جسم سياسة مستقبلية كامل:

```json
{
  "effective_from":"2026-11-01",
  "timezone":"Asia/Damascus",
  "working_days":[0,1,2,3,4,6],
  "start_time":"09:00",
  "end_time":"16:00",
  "grace_minutes":45,
  "grace_mode":"completed_blocks",
  "late_block_minutes":60,
  "overtime_multiplier":"2.00",
  "pairing_mode":"first_last",
  "duplicate_seconds":60,
  "finalize_after_minutes":120
}
```

الأحد=0، الجمعة=5، السبت=6. المنطقة الزمنية ثابتة للمكتب في النسخة الأولى. نسخة السياسة الجديدة لا تعيد كتابة يوم سابق.

## طريقة التسجيل المعتمدة: التسجيل على الجهاز ثم الربط

1. HR يحفظ سجل الموظف في EOMS.
2. المسؤول ينشئ المستخدم على iFace 880 Plus برقم غير مستخدم، ويسجّل بصمته من شاشة الجهاز.
3. يتحقق المسؤول يدوياً من تعرف الجهاز على الموظف تحت الرقم الصحيح.
4. HR يحدد الجهاز ورقم مستخدمه وتاريخ سريان الربط، ثم يستدعي POST `/attendance/devices/{id}/bindings`.
5. تعرض الواجهة «تم ربط رقم المستخدم». لا تعرض «تم التحقق إلكترونياً من البصمة»؛ هذه النسخة لا تفحص قالب البصمة على الجهاز.

لا يتطلب التسجيل اليدوي والربط اتصالاً مباشراً بين المتصفح والجهاز. جلب حركات الحضور ما زال يحتاج وسيلة نقل من الجهاز إلى السيرفر. لا تحجز هذه النسخة رقم مستخدم الجهاز تلقائياً، ولا تبدأ التسجيل عن بعد، ولا تخزن قالب الوجه أو البصمة في EOMS. لا يُستخدم biometric_code القديم وحده بدلاً من الربط المؤرخ.

## إرسال الحركات من الوسيط

`POST /api/v1/attendance/device-ingest`

Headers: `Accept: application/json`, `Content-Type: application/json`, و`Authorization: Bearer <DEVICE_TOKEN>`.

```json
{
  "events":[
    {"external_id":"stable-source-id-1001","device_user_id":"105","occurred_at":"2026-10-29T09:00:00+03:00","direction":"unknown"},
    {"external_id":"stable-source-id-1002","device_user_id":"105","occurred_at":"2026-10-29T16:00:00+03:00","direction":"unknown"}
  ],
  "complete_through":"2026-10-29T16:00:00+03:00"
}
```

- عدّل التواريخ إلى حركات حقيقية حدثت بالفعل؛ يمنع الوقت المستقبلي بأكثر من خمس دقائق. `complete_through` لا يجوز أن يكون في المستقبل مطلقاً.
- الحد 500 حدث لكل طلب و120 طلباً بالدقيقة لكل IP وفق middleware الحالي. `events: []` صالح كنبضة مزامنة.
- الوقت ISO 8601 مع offset أو Z، بدقة ثوانٍ في التخزين. توحّد الحركات إلى UTC، وتعرض بتوقيت المكتب. لا تُرسل توقيتاً بلا منطقة.
- `direction`: `unknown`, `in`, `out`. يجب أن يعكس معلومات المصدر، لا تخمين الوسيط.
- external_id ثابت لنفس حدث المصدر عبر المحاولات. لا تستخدم UUID جديداً في كل إعادة إرسال. إذا لم يوفر المصدر ID، يصمم المحوّل هوية مستقرة بعد فحص السجلات.
- تكرار المعرف بنفس المحتوى يعاد كـ duplicate. نفس المعرف بمحتوى مختلف يرفض الدفعة كاملة بـ422، ولا يُحدث المزامنة أو يحفظ أحداثاً جزئية.
- `complete_through` تعهد من الوسيط بأن كل سجلات الجهاز حتى ذلك الوقت أرسلت بنجاح، بما فيها الصفحات السابقة. ليس وقت آخر بصمة أو مجرد اتصال بالجهاز. لا ترسله عند الاستيراد الجزئي. يحافظ الخادم على أعلى قيمة ولا يرجع للخلف.
- الرد: `data.inserted`, `data.duplicates`, `data.unmatched`, `data.complete_through`.

لا تستخدم واجهة الفرونت العادية لتخزين توكن الجهاز. المسؤول ينقله مرة واحدة إلى إعدادات الوسيط الآمنة. لا يتم حذف سجلات الجهاز تلقائياً.

## عرض الحضور والتقارير

| المسار | الصلاحية والسلوك |
| --- | --- |
| GET `/attendance/days?date=2026-10-29` | `attendance.view`، قائمة إدارية عامة |
| GET `/employees/{id}/attendance?date=2026-10-29` | الموظف نفسه أو `attendance.view`؛ يرجع تفاصيل اليوم |
| GET `/attendance/days/{id}` | الموظف صاحب اليوم أو `attendance.view` |
| GET `/employees/{id}/attendance-report?from=2026-10-01&to=2026-10-31` | نفس النطاق، 31 يوماً كحد أقصى |

فلاتر القائمة: `employee_id`, `department_id`, `status`, `review_status=draft|approved`, `per_page=1..100`. الترقيم ببيانات `meta` و`links` الموجودة في المشروع. `summary.total` و`summary.by_status` محسوبان على كل النتائج المطابقة للفلاتر، وليس الصفحة الحالية.

تفاصيل اليوم ترجع `data.day`, `data.punches`, `data.corrections`. الحركات الأصلية غير قابلة للتعديل والحذف من هذه الواجهات.

أهم حقول اليوم:

| الحقل | المعنى |
| --- | --- |
| `employee` | id والرقم الوظيفي والاسم والقسم فقط؛ لا بيانات مالية أو رقم وطني |
| `policy` | النسخة والمنطقة والبداية والنهاية والسماح وطريقة تفسير الحركات |
| `work_date` | تاريخ يوم الدوام المحلي |
| `first_in`, `last_out` | أوقات ISO 8601 مع UTC أو null |
| `worked_minutes` | مدة فعلية بالدقائق أو null؛ السماح لا يضيف دقائق عمل وهمية |
| `late_actual_minutes`, `late_minutes`, `late_hours` | التأخير الفعلي، دقائق الشرائح المحتسبة، وساعاتها؛ ليست مبلغ خصم |
| `early_minutes` | الخروج المبكر؛ مستقل عن التأخير |
| `extra_minutes_unapproved` | البقاء بعد نهاية الجدول؛ معلومات لا استحقاق مالي |
| `status` | حالة الحضور الأساسية |
| `flags` | ملاحظات مستقلة يمكن أن تجتمع |
| `coverage_complete` | هل جميع الأجهزة المرتبطة بتلك الفترة أكدت المزامنة حتى نهاية الدوام؟ |
| `review_status`, `approved_at` | مسودة أو يوم معتمد |
| `pending_changes` | وصل اختلاف بعد الاعتماد ويتطلب إعادة فتح ومراجعة |
| `version` | رقم النسخة المطلوب لعمليات الكتابة المتعارضة |
| `permissions` | صلاحية طلب تصحيح/اعتماد/إعادة فتح؛ شروط اكتمال العملية يفحصها الخادم أيضاً |

حالات الحضور: `pending`, `present`, `incomplete`, `absent_unconfirmed`, `absent`, `day_off`, `outside_service`.

الأعلام: `inferred_first_last`, `duplicate_punch_ignored`, `multiple_punches_no_break_deduction`, `missing_or_ambiguous_punch`, `unclassified_punches`, `direction_conflict`, `sync_unconfirmed`, `manual_correction`, `work_on_day_off`, `punch_outside_service`, `leave_requires_review`.

وجود `present` لا يعني اعتماداً ولا اكتمال المزامنة. حركات اليوم غير موجودة قبل موعد الإغلاق تعني `pending`، وبعده تعني `absent_unconfirmed` إذا لم تكتمل المزامنة. يتحول إلى `absent` بعد 18:00 وفق الإعداد الافتراضي فقط عند تأكيد المصدر. تعطيل جهاز لا يستبعده بصمت من متطلبات المزامنة التاريخية. إذا لم يوجد أي ربط جهاز للموظف، لا يثبت غيابه آلياً.

التقرير يجمع أيام المجال بما فيها المجهولة، ويعيد `unknown_worked_days` حتى لا يُفهم مجموع المدد المعروفة على أنه وقت مكتمل لكل الشهر. `financial_effect_applied=false` دائماً. CSV/Excel والتصدير الخلفي ليست ضمن هذا الإصدار؛ يمكن للفرونت عرض وطباعة التقرير الحالي.

## التصحيح والاعتماد

1. الموظف يطلب تصحيح يومه، أو مستخدم `attendance.adjust` يطلب نيابة عن موظف.
2. POST `/attendance/days/{id}/corrections`:

```json
{"version":1,"type":"times","first_in":"2026-10-29T09:00:00+03:00","last_out":"2026-10-29T16:00:00+03:00","reason":"نسي الموظف تسجيل الخروج وتم التحقق"}
```

أو غياب مؤكد يدوياً: `{"version":1,"type":"absence","reason":"تم التحقق من الغياب يدوياً"}` دون أوقات. وقتا التصحيح يجب أن يكونا قد حدثا، في نفس اليوم المحلي وبترتيب صحيح. لا تدعم هذه النسخة تصحيح أيام الراحة أو ما خارج الخدمة. لا يوجد أكثر من طلب pending لليوم.

3. مراجع مختلف يملك `attendance.approve` يستخدم POST `/attendance/corrections/{id}/review` مع `decision=approve|reject`, و`reason` مطلوب. لا يمكن لأي شخص مراجعة طلبه بنفسه، حتى مسؤول النظام.
4. إذا وصل مصدر جديد بعد طلب التصحيح، يمنع قبول الطلب القديم بـ409؛ يمكن رفضه ثم إنشاء طلب جديد. التصحيح المعتمد يغيّر الملخص دون حذف المصدر.
5. POST `/attendance/days/{id}/approve` مع `version`. يلزم انتهاء ساعات الدوام، حالة مكتملة، عدم وجود طلب معلق، وتأكيد المزامنة أو تصحيح يدوي معتمد. لا يمكن اعتماد سجل ناقص.
6. الحركات الجديدة بعد الاعتماد تحفظ، لكن تبقى قيم اليوم ثابتة مع `pending_changes=true`.
7. POST `/attendance/days/{id}/reopen` مع `version`, `reason`، ثم راجع اليوم بعد إعادة حسابه. التصحيح اليدوي المعتمد السابق يبقى له الأولوية على الحركات ما لم يُستبدل بتصحيح معتمد أحدث.

اعتماد اليوم ليس إقفال رواتب شهرياً. لا يوجد حذف للتصحيحات أو إلغاء تاريخ مراجعتها. تغيير قرار معتمد يكون بإعادة فتح اليوم وطلب تصحيح جديد.

الصلاحية `attendance.view` عامة على مستوى المؤسسة مثل صلاحيات HR الحالية. لا تمنحها لمدير قسم إذا كان مطلوباً حصره بقسمه؛ تقييد نطاق المدير حسب الأقسام لم يُضف. الموظف ذو دور employee يستطيع فقط عرض نفسه وطلب تصحيح لنفسه دون هذه الصلاحية العامة.

## إعدادات الرواتب المستقبلية

يحفظ `overtime_multiplier` في نسخة السياسة بقيمة افتراضية `2.00`؛ ويمكن لـ HR تغييره من 1 إلى 10 بدقة منزلتين عشريتين. هذه قاعدة معدّة لمرحلة الرواتب فقط. لا تُضرب دقائق الحضور الفعلية في هذا المعامل ولا يُنشأ استحقاق مالي الآن.

عند بناء الرواتب لاحقاً: يحدد لكل موظف راتب أساسي وسعر ساعة مؤرخان، ثم الخصم = ساعات التأخير المحتسبة المعتمدة × سعر الساعة، وأجر الإضافي المعتمد = ساعاته × سعر الساعة × معامل الإضافي الساري. لا نخصم مرة بالتأخير المحتسب ومرة ثانية لنفس السبب بتخفيض ساعات العمل؛ قاعدة الراتب الشهرية ستحتاج اعتماداً مستقلاً.

`extra_minutes_unapproved` يبقى وقت البقاء بعد نهاية الدوام دون اعتماد مالي. لا توجد في هذا التحديث حقول سعر الساعة أو مسيرات الرواتب أو حساب إجمالي مستحقات الموظف. الراتب الأساسي الموجود في العقود لا يتحول تلقائياً إلى سعر ساعة بافتراض عدد أيام أو ساعات لم نتفق عليه.

## سلوك الفرونت

- الحضور، نقص الحركة، اكتمال المزامنة، والاعتماد أبعاد منفصلة؛ يمكن أن يظهر الموظف حاضراً ومتأخراً وغير معتمد معاً.
- اظهر null كـ«غير مكتمل»، و0 كصفر حقيقي. لا تحسب الغياب من غياب صف.
- استخدم timezone القادمة مع السياسة عند العرض، لا منطقة المتصفح تلقائياً. لا تضف +03 مرتين.
- عند 409 أعد جلب تفاصيل اليوم ثم اطلب مراجعة التغييرات، ولا تستبدل version تلقائياً ثم تعيد نفس قرار الاعتماد.
- 401 جلسة/اعتماد غير صالح، 403 لا صلاحية، 404 مورد غير موجود، 422 أخطاء المدخلات أو تعارض بيانات الاستيراد.
- عطّل أزرار الكتابة أثناء الطلب. إذا انقطع الاتصال بعد الإرسال، أعد جلب الحالة قبل المحاولة. توجد حماية من تكرار طلب تصحيح معلق أو إعادة مراجعة/اعتماد سابق.
- تعرض آخر مزامنة ومؤشر عدم اكتمال البيانات. لا يوجد WebSocket في هذه النسخة؛ يمكن تحديث الشاشة دورياً بفاصل معتدل.
- السبب مطلوب للتصحيح والمراجعة وإعادة الفتح، بطول 5 إلى 1000 حرف. تُسجّل هذه العمليات في AuditLogger داخل نفس المعاملة.

## ما يلزم قبل الإنتاج

تشغيل اختبارات الحضور والمجموعة الكاملة على MySQL/MariaDB، ثم تجربة وسيط الجهاز على سجلات حقيقية، وتجربة إعادة إرسال دفعة وانقطاع الاتصال، ومراجعة التوقيت. المتطلبات المتقدمة غير المنفذة: ADMS الأصلي، برنامج الوسيط نفسه، استيراد USB/CSV، جداول موظفين مختلفة، الدوام الليلي، تقويم الإجازات والعطل، قفل شهر الرواتب، واجهة تصدير الملفات وتقييد المدير حسب قسمه.


## بيئة التحقق من الحزمة

تم تشغيل PHP 8.5.12، واختبارات PHPUnit على SQLite بقاعدة ذاكرة منفصلة، وفحص Pint، وفحص صياغة PHP، وظهور مسارات API. لا يثبت SQLite سلوك أقفال InnoDB؛ أعد تشغيل المجموعة على MySQL/MariaDB المستخدم لديك قبل النشر، ثم اختبر التزامن واتصال الجهاز الحقيقي.

القسم المعروض في نتائج الأيام وفلتر القسم يعتمدان على قسم الموظف الحالي، وليس لقطة تاريخية لتوزيع الأقسام.

### تنبيه تبعيات مستقل

أبلغ `composer audit` أثناء التجهيز عن advisory متوسط للحزمة الموجودة أصلاً `symfony/mime` بالإصدار 8.1.7: `CVE-2026-45070`، ويتعلق بحقن ترويسات البريد. يشير التقرير إلى أن الإصلاح في 8.1.10 أو إصدار متوافق أحدث. لم تغيّر حزمة الحضور composer.json أو composer.lock؛ افحص التحديث الجزئي وشغّل الاختبارات قبل نشر خدمات البريد. المرجع الذي أعاده Composer: https://symfony.com/cve-2026-45070 .

التحديث المقترح للتبعية يكون بكوميت مستقل بعد التحقق:

```bash
composer update symfony/mime --with-dependencies
composer audit
php artisan test
```
