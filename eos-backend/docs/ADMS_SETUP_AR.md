# ربط EOMS بجهاز iFace 880 Plus عبر ADMS/PUSH

بني التعديل فوق commit `f2b3ee6bee26fbc9af124abeb70657ea565b8866` (الحضور V2).
المصدر: الملف المرفق ZKTeco_iFace880_Plus_ADMS_Remote_Fingerprint_Resource.md.
الجهاز الموصوف: Firmware ZMM720-NF43HB-Ver1.2.20، Push Service 2.0.33S-20220623.

المؤكد من المصدر: رفع ATTLOG وGET /iclock/getrequest عملا على الجهاز الحقيقي. تنفيذ USERINFO وENROLL_FP ونجاح التسجيل الفعلي لم يُثبت بعد. اختبارات هذا التعديل تحاكي HTTP/قاعدة البيانات؛ ليست اختباراً للجهاز.

## 1. كيف يعمل الاتصال وأين نضع IP؟

الجهاز هو الذي يبدأ الاتصال بخادم Laravel ويرفع الحركات ويسحب الأوامر. Laravel لا يفتح اتصالاً إلى منفذ الجهاز 4370، ولا يحتاج برنامج Bridge على اللابتوب عند وصول ADMS إلى الخادم مباشرة.

| العنوان | أين يوضع؟ | مثال المصدر |
|---|---|---|
| IP جهاز البصمة | أمر إعداد EOMS أدناه أو API connection، ويُحفظ في hr_attendance_devices.adms_source_ip | 10.42.0.61 |
| IP الكمبيوتر الذي يشغل Laravel | داخل الجهاز: Cloud Server Setting → Server Address | 10.42.0.1 |
| منفذ خادم Laravel للاختبار | داخل الجهاز: Server Port | 8088 |
| الرقم التسلسلي الحقيقي للجهاز | أمر الإعداد serial، ويُطابق SN في اتصال الجهاز | خذه من Device Info |

القيم السابقة أمثلة مأخوذة من التجربة السابقة، وليست عناوين ثابتة مدمجة بالكود. إذا تغير IP الجهاز بسبب DHCP حدّث الإعداد، أو احجز له عنواناً ثابتاً في DHCP. لا تضع IP الجهاز في APP_URL. لا تضع http:// أو /iclock في Server Address على الجهاز؛ الجهاز يضيف المسارات بنفسه.

IP في EOMS هو قيد لمصدر الاتصال، وليس عنواناً يتصل به التطبيق. يجب أن يطابق العنوان الذي يراه خادم PHP فعلياً. العنوان 10.42.0.61 خاص بالشبكة المحلية ولا يظهر بهذا الشكل لخادم إنترنت عبر NAT.

## 2. تثبيت التعديل

خذ نسخة احتياطية من قاعدة البيانات، ثم طبّق changes.patch من جذر مستودع EOMS، أو انسخ ملفات eos-backend الموجودة في الحزمة إلى الملفات المقابلة. لا تستخدم الطريقتين معاً.

```bash
git apply --check /path/to/changes.patch
git apply /path/to/changes.patch
cd eos-backend
php artisan optimize:clear
php artisan migrate
php artisan test
```

لا تستخدم migrate:fresh. التعديل لا يضيف حزم Composer ولا يغيّر ملف الاعتماديات. لا تستبدل .env بملف آخر؛ أضف القيم المذكورة لاحقاً فقط. استعمل قاعدة اختبارات منفصلة عن بيانات الموظفين.

## 3. أول اتصال محلي: نفس شبكة الجهاز والكمبيوتر

في `.env` الخاص بـ Laravel:

```dotenv
ATTENDANCE_ADMS_ENABLED=true
ATTENDANCE_ADMS_ALLOW_HTTP=true
ATTENDANCE_ADMS_REMOTE_ENROLLMENT=false
```

ALLOW_HTTP=true مخصص للشبكة المحلية المعزولة أو VPN محمي؛ لا تنشر بوابة HTTP الخام على الإنترنت.

ثم، من eos-backend:

```bash
php artisan optimize:clear
php artisan attendance:configure-adms YOUR_REAL_DEVICE_SERIAL 10.42.0.61
php artisan serve --host=0.0.0.0 --port=8088
```

**هنا تضع IP الخاص بالجهاز: المعامل الأخير للأمر.** استبدل YOUR_REAL_DEVICE_SERIAL بالرقم الحقيقي من الشاشة. مثال 10.42.0.61 يعمل فقط إن بقي عنوان جهازكم نفسه. الأمر ينشئ سجل جهاز جديد إن لم يوجد SN، أو يحدث اتصال السجل الموجود، ويعرض device ID. لا ينشئ موظفين أو بصمات ولا يثبت أن الجهاز اتصل فعلاً. السجل المعطل يبقى معطلاً حتى تفعّله عبر API المعتاد.

أوقف سكربت PHP probe القديم إن كان يستعمل 8088، لأن المنفذ لا يمكن أن يستخدمه الخادمان معاً. لا تحذف adms-archive القديم؛ البيانات التي أُقر باستلامها في التجربة القديمة تحتاج حفظاً/استيراداً مستقلاً، وقد لا يعيد الجهاز إرسالها. هذا التعديل لا يستورد ملفات ذلك الأرشيف تلقائياً.

على الجهاز، Menu → Comm. → Cloud Server Setting:

- Server Mode: ADMS.
- Server Address: عنوان Ethernet للكمبيوتر الذي يشغل Laravel؛ في المصدر 10.42.0.1.
- Server Port: 8088.
- Enable Domain Name: OFF عند استخدام IP.
- Proxy: OFF.
- HTTPS: OFF للتجربة المحلية فقط.

هذه الإعدادات تعتمد على أن Ethernet/المشاركة يعملان كما في المصدر. اسمح في جدار الكمبيوتر بالمنفذ 8088 من جهاز البصمة فقط. احتفظ بإعدادات Cloud Server السابقة قبل استبدالها. خادم artisan serve للاختبار، وليس للنشر الإنتاجي.

## 4. التأكد من الاتصال

استخدم GET /api/v1/attendance/devices بحساب لديه attendance.manage وراقب تغير last_seen_at. قيمة connection_mode يجب أن تكون adms. سجّل حركة تجريبية ثم راقب punches عبر واجهات حضور الموظف أو unmatched-punches إن لم يُربط PIN بعد.

يجب أن يطابق device_user_id في ربط الموظف PIN المخزن على الجهاز، مع الحفاظ على الأصفار إن وجدت. لا تفترض أنه يساوي employee.id. الواجهات القديمة لإنشاء الربط تبقى كما هي:

```http
POST /api/v1/attendance/devices/DEVICE_ID/bindings
Authorization: Bearer HR_TOKEN
Content-Type: application/json

{"employee_id":123,"device_user_id":"00105","valid_from":"2026-11-05"}
```

اربط كل رقم بتاريخ سريان مناسب قبل احتساب حركاته، ولا تربط رقم شخص آخر. يمكن ربط الحركات غير المعروفة لاحقاً بالخدمة الموجودة.

## 5. تعديل الاتصال من الفرونت/Postman

```http
PATCH /api/v1/attendance/devices/DEVICE_ID/connection
Authorization: Bearer HR_TOKEN
Content-Type: application/json

{"connection_mode":"adms","adms_source_ip":"10.42.0.61"}
```

تتطلب attendance.manage. الاختيار خاص بكل جهاز؛ الأجهزة الموجودة تبقى bridge إلى أن تحولها صراحة. بعد التحويل لا يقبل الجهاز نقطة JSON القديمة device-ingest، حتى لا تتجاوز ضمانات ADMS باستخدام توكن Bridge قديم.

للعودة الصريحة إلى Bridge:

```json
{"connection_mode":"bridge"}
```

تغيير الاتصال يمسح complete_through السابق ويضع الأيام المعتمدة ذات الصلة قيد مراجعة تغيّر المصادر، مع إبقاء قيمها المعتمدة. لا يمكن تبديل الاتصال أثناء مهمة تسجيل فعالة حتى تنتهي أو تنقضي مهلتها.

## 6. الخادم على الإنترنت: ترتيب الربط الصحيح

لا تضع 10.42.0.61 كعنوان جهاز متوقع على خادم إنترنت ثم تتوقع أن يتطابق؛ NAT يغير المصدر. للنشر اعتمد شبكة VPN بين موقع الجهاز والخادم تحافظ على عناوين الأجهزة، واضبط Server Address على عنوان الخادم داخل الشبكة المحمية، وadms_source_ip على عنوان مصدر الجهاز الذي يصل فعلياً داخلها.

الجهاز لا ينشئ VPN بمجرد وضع IP. يمكن لراوتر المكتب أو مضيف Gateway مخصص توفير VPN وتوجيه الحركات. اللابتوب في تجربة المصدر يجب أن يبقى عاملاً طالما هو الذي يوفر الطريق الشبكي؛ وجود سيرفر إنترنت لا يحول جهاز LAN إلى جهاز عام تلقائياً.

رقم SN وIP allowlist ليسا توقيعاً مشفراً أو اعتماد جهاز قوياً. هذا التنفيذ يتطلب شبكة أجهزة موثوقة ومعزولة وقيود جدار ناري؛ لا يُنشر اعتماداً على SN وحده على الإنترنت حتى مع HTTPS. دعم هوية PUSH الأقوى يحتاج وثائق SDK وإصدار Firmware المتوافق، وهو غير مدّعى في هذه الحزمة.

عند Nginx + PHP-FPM يجب أن ينقل FastCGI قيمة REMOTE_ADDR الحقيقية للمصدر الذي تسمح به الشبكة. الوسيط الحالي يتجاهل X-Forwarded-For لمنع انتحال IP. لا تضع IP مشتركاً لبروكسي عام مكان IP الجهاز لكي تتجاوز 403. لو توجد طبقة HTTP reverse proxy إضافية تُخفي المصدر، يلزم ضبط معماري موثوق يحافظ على المصدر ويفرض القيود في نقطة الدخول قبل تشغيل التكامل. لا تستخدم trustProxies('*') عشوائياً.

يجب تمرير المسارات /iclock/* كما هي إلى Laravel، دون /api، ودون توجيه إلى صفحة Angular أو تحويل HTTP إلى HTTPS لا يدعمه الجهاز. المنفذ 4370 ليس منفذ ADMS. قيد حجم الطلب عند Nginx إلى 1 MiB أو أقل متوافق مع config؛ التطبيق يرفض أكثر من 1 MiB أو 5000 سجل في الطلب. الملفات الأصلية للحضور تحفظ في قاعدة البيانات، لذا امنع تسجيل body الخاص بهذه المسارات في access/APM logs وخذ نسخاً احتياطية محمية لقاعدة البيانات.

## 7. ما الذي يستقبله الخادم؟

- GET /iclock/cdata: تهيئة PUSH؛ نطلب ATTLOGStamp=0، ولا نستخدم قيمة 9999 المختبرية التي قد تخفي سجلات قديمة. التهيئة لا تضمن أن firmware سيعيد الأرشيف الذي سبق إقراره.
- POST /iclock/cdata?table=ATTLOG: نص TAB، ويحفظ الطلب الأصلي والحركات في معاملة واحدة قبل OK: N.
- GET /iclock/getrequest: سحب أمر واحد أو OK.
- POST أو GET /iclock/devicecmd: إقرار معرف الأمر ونوعه ونتيجته.
- /iclock/ping و/iclock/registry: تحديث آخر اتصال.
- نظائر .aspx مدعومة.
- table=options يُقبل لتحديث الاتصال دون حفظ محتواه.
- القوالب البيومترية وOPERLOG والأنواع غير المدعومة لا تُحفظ ولا تُؤكد؛ تحصل على 503. هذه بوابة للحضور وصيغ التجربة المرفقة، وليست تنفيذ SDK كامل. إذا رفع جهازكم نوعاً آخر باستمرار نحتاج عينة منقحة من نوع/صيغة الطلب فقط، دون بيانات البصمة، لإضافة معالجة صحيحة بدلاً من إسقاطها.

صيغة ATTLOG المدعومة:

```text
PIN<TAB>YYYY-MM-DD HH:MM:SS<TAB>status<TAB>verify<TAB>...
```

status=0 دخول، 1 خروج، البقية unknown. سياسة first_last الافتراضية تحتفظ بحساب أول/آخر حركة. التوقيت من timezone الجهاز المسجل، ويُحوّل إلى UTC. تُحفظ الأصفار في PIN. التكرار يُمنع بمفتاح مشتق من سطر الحركة، حتى عند إعادة تجميع الدفعات أو اختلاف نهايات السطور. الحركات غير المرتبطة محفوظة لحين ربط الموظف. عند فشل التخزين لا نرسل OK؛ يعيد الجهاز الطلب.

**اكتمال التزامن:** لا نرفع complete_through من heartbeat أو أحدث بصمة. لذلك يمكن أن تظل الأيام absent_unconfirmed أو غير قابلة للاعتماد حتى تُراجع/تُصحح يدوياً وفق الواجهات الحالية. لا تعتمد الغياب أو الرواتب آلياً قبل إضافة وسيلة مثبتة لمصالحة كامل سجل الجهاز؛ مراقبة آخر اتصال وحدها لا تكفي. هذا القيد مقصود لتفادي غياب خاطئ عند فقد بيانات.

## 8. تسجيل البصمة عن بُعد — تجربة اختيارية

طريقة التسجيل على الجهاز ثم الربط تعمل دون تشغيل هذه الميزة. إذا أردت تجربة الزر من Angular، استخدم موظف اختبار وPIN غير مستخدم تماماً على الجهاز، وتأكد محلياً من ذلك أولاً. USERINFO قد يعدل بيانات مستخدم موجود، ومنها الاسم/الصلاحيات/حقول أخرى؛ لا تستخدم PIN مسؤول الجهاز أو موظف حقيقي في الاختبار الأول. لا يوجد فحص إلكتروني لقائمة المستخدمين/البصمات الحالية في هذه النسخة.

فعّل مؤقتاً:

```dotenv
ATTENDANCE_ADMS_REMOTE_ENROLLMENT=true
```

ثم php artisan optimize:clear. أنشئ الموظف التجريبي واربط PIN تجريبياً عبر واجهة bindings المعتادة. الربط هنا ربط رقم فقط، ولا يعني أن بصمة قد حُفظت.

```http
POST /api/v1/attendance/bindings/BINDING_ID/enroll-fingerprint
Authorization: Bearer HR_TOKEN
Content-Type: application/json

{"finger_id":0,"confirm_user_update":true}
```

الحالة queued_user. عند سحب الجهاز يرسل النظام USERINFO؛ بعد ACK مطابق ID + CMD=DATA + Return=0 فقط، يجهز ENROLL_FP مع RETRY=3 وOVERWRITE=0. لا يرسل بصمة حقيقية أو قالباً بيومترياً. اسم التجربة على الجهاز EOMS_PIN باستخدام ASCII لتفادي اختلاف encoding الأسماء العربية.

الواجهة تتابع كل 2–5 ثوان:

```http
GET /api/v1/attendance/fingerprint-enrollments/ENROLLMENT_ID
Authorization: Bearer HR_TOKEN
```

الحالات: queued_user → await_user_ack → queued_enroll → await_enroll_ack → awaiting_physical_verification. الفشل failed، والمهلة timeout. المهلة الإجمالية الافتراضية خمس دقائق. يوجد قفل جهاز واحد يمنع أكثر من تسجيل فعّال على الجهاز. لا يعيد النظام إرسال أمر استلمه الجهاز آلياً إذا ضاع ACK، لأن تنفيذه قد حدث؛ افحص الجهاز قبل بدء محاولة جديدة. انتهاء المهلة لا يلغي شاشة أو أمراً سبق تنفيذه فعلياً على الجهاز.

حتى لو ظهر Return=0 يبقى biometric_verified=false. يجب أن تظهر شاشة التسجيل، وأن يضع الموظف إصبعه، ثم يجري تحققاً منفصلاً ببصمته تحت PIN الصحيح. بعد أن يشاهد HR هذا الاختبار يمكنه توثيق تأكيده اليدوي:

```http
POST /api/v1/attendance/fingerprint-enrollments/ENROLLMENT_ID/confirm
Authorization: Bearer HR_TOKEN
Content-Type: application/json

{"physical_test_passed":true,"note":"شاهدت تحققاً منفصلاً ببصمة الموظف تحت الرقم الصحيح"}
```

تتحول الحالة manually_confirmed مع هوية المسؤول ووقت وملاحظة. operator_confirmed=true؛ biometric_verified يظل false لأن الخادم لا يتحقق من قالب البصمة بنفسه. لا تُعرض عبارة «تم التحقق الإلكتروني من البصمة». رفض الأمر أو عدم ظهور الشاشة يتطلب اختبار Firmware/SDK؛ لا نعد التسجيل مدعوماً فعلياً قبل نجاح التجربة.

## 9. ماذا ترفع إلى Git؟

ارفع ملفات الكود والاختبارات وconfig و.env.example وdocs فقط. لا ترفع .env أو توكنات أو سجلات/أرشيف الحضور أو vendor أو ZIP التسليم. اسم commit مقترح:

